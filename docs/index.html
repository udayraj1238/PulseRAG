EXHIBIT A — METHOD

Four checkpoints, in order

Standard RAG has two steps. This has four — the extra two are where the actual verification happens.

01 / RETRIEVE
Search the corpus
Semantic cache checked first — a 92%-similar paraphrase counts as a hit. Otherwise, vector search across 500 indexed papers in Qdrant.
02 / GRADE
Interrogate what came back
Vector similarity finds "related." An LLM grader checks each chunk for "actually useful" — a real, separate judgment call.
this is where most RAG pipelines just trust the search results blindly
03 / WRITE
Generate, constrained
The answer is written using only chunks that survived grading. Fewer than 2 pass → the query is rewritten and search runs again, capped at 2 attempts.
04 / VERIFY
Cross-examine the answer
The generated answer is split into sentences. Each one is checked, independently, against the source chunks. Anything unsupported gets flagged before you see it.

EXHIBIT C — FINDINGS

Six mechanisms, examined

Each finding below was verified against the source code, not taken on faith.

01
Relevance grading, not just similarity
grade_relevance.py runs an independent LLM judgment on every retrieved chunk before it's trusted.
CONFIRMED
02
Bounded query rewriting
Rewrites trigger automatically on weak retrieval, capped at 2 attempts — verified it cannot loop indefinitely.
CONFIRMED
03
Sentence-level hallucination scoring
Risk is a confidence-weighted fraction of ungrounded sentences — not a single opaque number.
CONFIRMED
04
Semantic caching at 0.92 similarity
Paraphrased queries share a cache entry — confirmed via direct threshold testing, not assumed.
CONFIRMED
05
Explicit graph state, not implicit control flow
Built as a LangGraph state machine — the retry loop is a named conditional edge, inspectable on its own.
CONFIRMED
06
Feedback loop to Postgres
Every conversation and its risk score is logged — thumbs-down ratings can trace back to specific bad source chunks.
CONFIRMED
